### A.2 为什么不给这些源写 JS 解释器

74 条候选里有 59 条的核心规则是 `@js:` 块。它们的典型形态是：

```js
var body = { q: "{{key}}", page: Math.max(0, page-1), pageSize: 20 };
var option = { method:"POST", body: JSON.stringify(body), headers:{...} };
java.put("url", String(url + "," + JSON.stringify(option)));
```

这段 JS 做的事只有三件：**拼 JSON、指定 header、把结果塞进 `java.put`**。真去实现一个 JS 子集解释器（含 `java.ajax`/`cookie.getCookie`/`JSON.stringify`）风险极高、收益极低；把这几个站点的接口按声明式重写一遍，代码量不到 200 行且能被单测覆盖。

所以本轮采取的策略是：**规则层做不到的，就为站点写一个小的原生适配器**，接口抽象成统一的 `search / detail / toc / chapter`（详见 `src/lib/lightnovel.js` 头部注释）。

### A.3 一个重要的判定修正

上一轮 `classify()` 是「整份 JSON 正则扫一遍，出现 `@js`/`<js>` 就判死」，导致大量本来能用的源被误杀。典型误杀：

```
ruleSearch.coverUrl: "a.0@href<js>var id=...; '/files/image/'+iid+'/'+id+'s.jpg';</js>"
```

封面地址里塞了一段 JS，但书名、书页地址、目录、正文全是纯选择器 —— 这种源缺封面完全不影响阅读。

本轮改成按字段分级：

- **关键字段**（searchUrl、bookList、name、bookUrl、chapterList、chapterName、chapterUrl、content）含 JS/XPath → 判 `unsupported`，并指出是哪个字段；
- **次要字段**（coverUrl、kind、wordCount、lastChapter、bookInfo.init、intro）含 JS → 只记 `notes`，实际解析时跳过该字段；
- `loginUrl` / 代理标注 / 人机验证 → 降到 `partial`（可登录后使用），不再判死。

改完后同一批候选里「非不兼容」从 16 条升到 15 条 ok + 若干 partial（数量变化不大，但**判定理由准确了**，报告里能说清每条到底卡在哪一步）。

## C. 三种「下载能力」的区分（用户特别要求）

这是本报告最容易含混的地方，逐个站点分开说：

| 能力 | 定义 | 轻之国度 | 鲸云 | 其他候选源 |
| --- | --- | --- | --- | --- |
| **① 在线阅读** | 打开章节能读到正文 | ✅ 25080 字/章 | ✅ 3645 字/章 | ⚫ 全部未通过搜索或站点不可达 |
| **② 阅读器逐章离线下载** | 阅读器自己按章抓取并落盘，支持断点/重试/记录 | ✅ **88/88 章全下**，117.79 万字，3.27MB，171 秒 | ✅ 258 章目录，抽样 12/12 章节全成功 | ⚫ 无 |
| **③ 网站成品文件下载** | 站点自己提供 EPUB/TXT 直链 | ❌ 接口有 `epub_ready` / `epub_download_url` 字段，但**实测 10 本书全是 `epub_ready=0`、URL 为空**，站点没有成品文件 | ❌ 接口无此字段，页面也没有 EPUB/TXT 链接 | ❌ 未发现 |

**② 的实现方式（不依赖站点整本接口）**：

```
取目录（卷 → 章） → 逐章 GET/POST 正文 → 解析成纯文本 → 写 缓存/正文.txt
                                              ↓ 失败
                                        进重试队列，下次接着下
```

不是「调一个整本接口拿 zip」，所以任何站点只要单章能读，整本就能下 —— 轻之国度 88 章的实测就是这个流程跑出来的。

### D.1 解析器为本轮做的扩展

1. **`@css:` 前缀剥离** — 大量源写 `@css: div > div > a@href`，之前会把 `@css:` 当类名，一条都取不到。

## F. 搜索与来源去重

### F.1 新源如何进入全局搜索

轻小说源不是独立搜索框，而是作为 `record.kind === 'ln'` 的记录进入 `STORE.srcList`，与书海阁、Legado 导入源共用一条流水线：

```
启用源列表 → 按优先级排序 → 分批并发（默认 3） → 单源独立超时/重试
   → 谁先回来先展示（onPartial） → 全部回来后统一分组去重 → 排序
```

- 首次启动时 `ensureLNRecords()` 自动补齐内置轻小说源；已有记录不动（保留用户的启用状态和优先级）。
- 默认 `enabled: true`、`priority: 20+`（排在书海阁之后，避免拖慢主站搜索）。
- 单源超时不影响其它源，失败只记 `lastError`，不永久禁用。

### F.2 去重（沿用上一轮的 `dedupe.js`，无改动）

本次新增的两个源**属于不同站点、不同作品库**，实测同名率很低（轻之国度偏日轻官方译本，鲸云偏原创/同人），但机制已就位：

- 书名归一（繁简转换 + 去噪声词） + 作者归一 + 编辑距离相似度；
- 书名同 + 作者同 → 合并，保留 `sources[]`，详情页可切换；
- 书名同 + 作者不同 → **不合并**（任务明确要求）；
- 相似度 < 0.86 且有疑义 → 保留独立条目。

搜索结果里同一本书只显示一条，右侧显示「N 个来源」；点进详情可看各源的最新章节、是否需登录、源状态，切源后重新抓目录（不串源）。

### F.3 缓存与防重复请求

`search.js` 的 `createCache(ttl=10min)` 已实现：同一关键词短时复用、同源同词不重复并发（`once()`）、主动「重搜」才发新请求、源更新清缓存、切换来源只请求没搜过的源。本轮未改，直接复用。

### K.3 真机抓到并修掉的 4 个问题

这四条**在电脑端的 235 项单测里全绿，只有上机才暴露**：

1. **鲸云目录永远抓不到（严重）** —— `src/lib/sources.js` 的 `lnSourceAdapter.tocAll` 里把抓取回调返回值当 `{text}` 取，而页面层实际返回**裸字符串**。结果 `site.tocAll` 收到 null 直接返回空数组，界面报「目录没抓到」而请求明明是 200、56285 字节。已改成两种约定都认，并补了 4 条单测锁死。
2. **从书架/非搜索路径打开的书源识别失败** —— `openBook` 没有先 `ensureStore()`，`srcRecord` 返回 null，书被误判成「书海阁」走原生解析，轻小说源的目录必然抓不到。已在 `openBook` 开头补 `await this.ensureStore()`。
3. **热词/历史 chip 左侧点不动（触控死区）** —— 设备在逻辑 `x < 65` 时静默丢弃触摸事件，而第一个 chip 起点在 x≈38。已把标签固定成 50px 宽，chip 起点移到 x≈68。
4. **简介混进 CSS 残片** —— 站点把 summary 截断在 HTML 标签中间，漏出 `[font=webfont, 微软雅黑, "Microso` 并在设备上当成正文显示。已加 `cleanIntro()` 清洗。
